## 1. 다음 앱 예측 — top-1은 "직전 앱으로 돌아가기"와 비슷, top-3에서 앞섬

재현: `uv run --group ml --group wake python -m ml.train_next_app --data <behacom_slim.csv>`

- 같은 분에 여러 번 찍힌 행은 마지막 하나만 쓴다(BEHACOM 중복; 지우기 전에는 가짜 A→B→A가 생겨 숫자가 부풀었다). 세션은 원래 시각의 간격(10분 이상)으로 나눈다.
- 같은 exe가 이어진 분들을 한 "방문"으로 묶는다(`devdesk.categories.exe_stem`: `firefox.exe` = `firefox`). 머문 시간 = 첫 분부터 마지막 분까지(행 수가 아니라 경과 시간: BEHACOM은 약 70초마다 찍는다).
- 문제: 지금까지의 방문(세션 안 최근 20개)으로 **다음에 바꿀 앱**을 맞힌다. 앱은 학습 데이터에서 많이 쓴 30개 + 기타(테스트 정답의 6.7 %).
- 사용자별 시간순 분할: 앞 70 % 학습 / 15 % 검증 / 15 % 테스트. 정답 방문이 다음 구간에 있는 예제는 뺀다(학습이 검증 데이터를 보지 않게) → 예제 9,033 / 1,925 / 1,903.
- 모든 모델에 같은 규칙: 지금 쓰는 앱은 다음 앱 후보에서 뺀다(방문은 앱이 바뀌어야 끝나므로).

| 모델 | top-1 | top-3 | 사용자별 평균 top-1 |
|---|---|---|---|
| 직전 앱으로 돌아가기 (A→B→A) | 0.446 | 0.632 | 0.480 |
| 사용자별 전이 빈도 (마르코프) | 0.408 | 0.690 | 0.448 |
| LightGBM (사용자, 현재·이전 2개 앱, 시간, 머문 시간) | 0.445 | 0.742 | 0.471 |
| **GRU** (최근 20 방문: 앱 임베딩 + 머문 시간 + 시각, 사용자 임베딩) | **0.469** | **0.753** | **0.489** |
| GRU, seed 5개 범위 | 0.459 – 0.469 | 0.750 – 0.765 | |

표의 GRU는 seed 42 하나이고, 5개 중 top-1이 **가장 높은** 경우였다.

GRU(seed 42) − 다른 모델, 95 % 구간. 테스트 **세션**을 통째로 2,000번 다시 뽑음(쌍 블록 부트스트랩: 한 세션 안의 예제는 서로 독립이 아니라서 행 단위로 뽑으면 구간이 좁게 나온다):

| 비교 | top-1 | top-3 |
|---|---|---|
| GRU − 돌아가기 | +0.3 ~ +4.3 %p (가장 좋은 seed에서 겨우) | +8.6 ~ +15.3 %p |
| GRU − 마르코프 | +2.8 ~ +9.6 %p | +3.7 ~ +9.0 %p |
| GRU − LightGBM | +0.3 ~ +4.3 %p | −1.2 ~ +3.2 %p (차이 없음) |

읽는 법: "직전 앱으로 돌아간다"만으로 44.6 %를 맞힌다(작업 중 두 앱을 오가는 습관). top-1에서 GRU는 1–2 %p 높지만 가장 좋은 seed에서도 구간 아래쪽이 +0.3 %p이고, 가장 나쁜 seed(0.459)는 +1.3 %p뿐이다 → **"비슷하다"가 정직한 결론**. top-3에서는 어느 seed든 돌아가기보다 10 %p 이상 높다(두 번째·세 번째 후보를 잘 고른다). top-3에서 GRU와 LightGBM은 같다. 데이터 정리를 고칠 때마다(중복 행, 세션 경계) top-1 구간이 0 근처를 오갔다.

## 2. 집중 이탈 예측 — "다음 10분 중 업무 시간"으로 바꿔서 했다 (2026-11-02)

**10-31에 멈춘 이유.** 집중을 "IDE/터미널 + 최근 1분 안에 입력"으로, 이탈을 "다음 10분 안에 집중이 아닌 분이 1분이라도 있음"으로 정했다. 그러자 집중 분이 2,076분뿐이었고, 그중 94 %가 이탈이었다. 10초짜리 검색도 이탈로 셌기 때문이다. 이 94 %는 그때 즉석에서 계산한 값이고 코드로 남아 있지 않다.

**바꾼 정의** (`ml/work_share.py`):
- **업무 분:** IDE/터미널 **또는 문서 앱**(LibreOffice, Word, PowerPoint, Excel, PDF 뷰어, Mendeley, AutoCAD, Inkscape 등 `DOCS`)이면서 최근 1분 안에 입력이 있는 분.
  - 브라우저는 업무로 치지 않는다. 주소를 모르면 공부인지 노는 건지 알 수 없다.
  - BEHACOM 원본(12,051열)에도 주소·창 제목 열은 없다. 앱 이름, 키·마우스 통계, CPU·메모리, 네트워크 양뿐이다.
- **정답:** 업무 분인 시점에서, **다음 H분 중 업무에 쓴 비율**(0~1).
  - "몇 분 떠나면 이탈"이라는 임의 기준이 없다. 10초짜리 검색은 10분 중 1분만 깎는다.
  - BEHACOM은 약 70초마다 기록해서 빠진 분이 있다. 그래서 다음 H분 중 기록이 있는 분만 세고, 절반 이상에 기록이 있어야 쓴다.
- **"자연스러운 이탈 기준"이 있는지도 확인했다.** 업무 앱을 떠났다 돌아오기까지의 시간은 1–2분 26 %, 2–3분 15 %, 3–5분 17 %, 5–10분 15 %, 10–20분 11 %, 20–60분 10 %, 60분 이상 6 %로 고르게 줄어든다. "잠깐 확인"과 "휴식" 사이의 골짜기가 없다(`figures/work_share.png` 왼쪽). 그래서 기준 하나를 고르는 대신 위의 비율을 정답으로 썼다.

**데이터:**
- 업무 분: 2,007 → 6,641분(문서 앱 추가). 500분 이상인 사람은 6명.
- 결정 시점: 11명, H=10에서 학습 4,381 / 검증 915 / 테스트 943.
- 사람마다 시간 순서로 70/15/15로 나눴다. 정답 구간(다음 H분)이 다음 부분에 걸치는 시점은 뺐다.
- 정답이 0~10분에 넓게 퍼져 있다(표준편차 3.5분). 8분 이상인 경우가 29 %다.

**모델:**
- 사람별 평균, "직전 H분처럼".
- LightGBM: 최근 5·15분의 업무·입력·전환·분류 비율, 지금 업무가 몇 분째인지, 세션 시간, 시각, 사용자.
- GRU: 최근 30행의 순서.
- 각 모델은 두 가지 특징 묶음으로 돌렸다.
  - **base:** DevDesk가 지금 기록하는 것만.
  - **+추가 정보:** BEHACOM에만 있는 받은·보낸 바이트, 단어 수, 지운 키 수, 스크롤, 앞에 띄운 시간, 앱 CPU. 실험 전용이다. DevDesk는 키보드 훅을 쓰지 않는다.

테스트 MAE(분, 낮을수록 좋음). 괄호 안은 사람별 평균과의 차이에 대한 세션 단위 블록 부트스트랩 95 % 구간이다(음수 = 더 잘함). ✓는 구간 전체가 0보다 작은 경우다. 표는 `work_share_model_behacom_metrics.json`에서 그대로 옮겼다. GRU는 시드 42의 값이다.

| 모델 | H = 5 | H = 10 | H = 15 |
|---|---|---|---|
| 사람별 평균 | 1.47 | 2.66 | 3.80 |
| 직전 H분처럼 | 1.40 (−0.25..+0.12) | 2.49 (−0.62..+0.25) | 3.66 (−0.82..+0.49) |
| LightGBM (base) | 1.31 (−0.25..−0.06) ✓ | 2.37 (−0.48..−0.08) ✓ | 3.37 (−0.73..−0.07) ✓ |
| GRU (base) | 1.25 (−0.35..−0.08) ✓ | 2.29 (−0.64..−0.11) ✓ | 3.33 (−0.86..−0.06) ✓ |
| LightGBM (+추가 정보) | 1.29 (−0.29..−0.06) ✓ | 2.25 (−0.66..−0.15) ✓ | 3.20 (−0.97..−0.14) ✓ |
| GRU (+추가 정보) | 1.22 (−0.39..−0.10) ✓ | 2.31 (−0.63..−0.04) ✓ | 3.28 (−1.03..+0.03) |

GRU는 시드 3개를 돌렸다. H=10에서 base는 2.29–2.35, +추가 정보는 2.18–2.31이었다. 시드에 따른 차이(H=10에서 base 0.07분, +추가 정보 0.13분)가 GRU와 LightGBM(base)의 차이 0.09분과 비슷하다.

**읽는 법:**
- **DevDesk가 기록하는 정보만 쓴 LightGBM과 GRU(base)는 세 H 모두에서 사람별 평균보다 유의하게 낫다.** H=10에서는 0.3–0.4분(약 11–14 %) 덜 틀리고, 세 H를 통틀어서는 11–15 % 덜 틀린다. "직전 H분처럼"은 구간이 0을 넘어 평균과 구별되지 않는다. H를 바꿔도 결론이 같아서, 10분이라는 선택에 결론이 기대지 않는다.
- **GRU와 LightGBM은 비슷하다.** 차이가 시드 차이 안에 있다. 딥러닝의 장점은 특징을 직접 만들지 않고 순서에서 배운다는 점이지, 정확도가 아니다.
- **추가 정보의 효과는 작다.**
  - LightGBM은 H=10에서 2.37 → 2.25, H=15에서 3.37 → 3.20으로 조금 좋아졌다.
  - GRU(+추가 정보)는 H=15에서 구간이 0을 넘었다. 시드에 따라 base보다 좋기도 나쁘기도 해서, GRU에 대해서는 "도움이 된다"고 말할 수 없다.
- **이 절의 테스트 세트는 세 번 쟀다**(코드 리뷰 두 라운드).
  1. 리뷰가 데이터 결함을 찾아 고쳤다. 설명서상 최대 60초인 "앞에 띄운 시간"에 857,627초까지 있었고(0.03 % 행), 0–60초로 잘랐다. CPU는 처음에 100으로 잘랐다가, 여러 코어 값(최대 334 %, 0.6 % 행)이 실제라서 자르지 않는 것으로 되돌렸다.
  2. 두 수정 모두 "+추가 정보" 줄만 바꿨다. GRU(+추가 정보) H=10은 2.29 → 2.39 → 2.31로 움직였다. base 줄은 세 번 모두 같았다.
  3. 그래서 base 결론은 테스트 결과를 보고 바꾼 것이 없다. "+추가 정보" 숫자는 테스트를 본 뒤 고친 결과이므로 대략으로 읽는다. 브라우저의 네트워크 양 같은 "주소 없는 단서"가 도움이 될 수는 있지만 작다. 브라우저를 제대로 나누려면 아래의 브라우저 확장이 필요하다.
- **한계:**
  - 정답은 "업무 앱을 계속 쓰는가"이지 실제 집중도가 아니다.
  - 문서 앱 목록(`DOCS`)과 H는 사람이 정했다. 결과를 본 뒤에는 바꾸지 않았다.
  - 브라우저 시간(전체의 49 %)은 업무에서 통째로 빠져 있다.
  - 측정 단계에서 분 번호 버그를 한 번 고쳤다(`docs/troubleshooting.md` 2026-11-02). 모델 크기·학습률 같은 설정은 테스트 결과를 보고 바꾸지 않았다. "+추가 정보" 특징만 위와 같이 두 번 고쳤다.

**다음: 브라우저 확장**(발표 뒤, 2026-10-30에 정한 방향).
- 크롬 확장이 브라우저 **안에서** 도메인을 분류한다(개발 / 공부 / 오락 / SNS / 기타).
- DevDesk에는 분류 이름 하나만 보낸다. 주소·제목·도메인은 보내지 않는다.
- 기본은 꺼짐이고, 이 분류로 잠금을 걸지 않는다.
- 그러면 지금 버리는 브라우저 49 %를 업무/비업무로 나눌 수 있다.

## 3. 하루 패턴 이상 탐지 — 오토인코더가 단순한 방법을 못 이김

재현: `uv run --group ml --group wake python -m ml.train_day_anomaly --data <behacom_slim.csv>`

- 하루 프로필 = 24시간 × (카테고리 6개 비율 + 입력 있음 비율) = 168개 값(서머타임 해제일에 두 번 있는 시간도 1을 넘지 않게 자름). 60분 미만인 날, 7일 미만인 사용자는 뺌 → 10명 301일(학습 214 / 테스트 87, 사용자별 날짜순).
- 공개 데이터에 "이상한 날" 정답이 없어 대리 평가(AUC, 0.5 = 찍기):
  - **새벽 게임**: 테스트 날의 0–5시 사이 3시간을 게임으로 덮어씀. 값은 그날 가장 꽉 찬 시간과 같은 크기(1.0으로 넣으면 BEHACOM은 약 70초 간격이라 정상 날이 넘지 못하는 크기여서, "새벽 게임"이 아니라 "값이 너무 큼"을 잡게 된다; 고치기 전 PCA 0.979)
  - **6시간 밀림**: 하루 전체를 6시간 뒤로
  - **다른 사람의 하루**: 다른 사용자의 날을 "이 사람 날"이라고 넣음

| 방법 | 새벽 게임 | 6시간 밀림 | 다른 사람 |
|---|---|---|---|
| 사용자 평균 하루와의 거리 | 0.823 | **0.647** | **0.658** |
| PCA 8성분 복원 오차 (모든 사용자) | **0.961** | 0.600 | 0.500 |
| 조건부 오토인코더 (사용자 임베딩, seed 3개 평균; early stopping = 사용자별 학습일 마지막 15 %) | 0.925 | 0.613 | 0.611 |

- 오토인코더 seed 사이 범위: 새벽 게임 0.91–0.93, 밀림 0.60–0.62, 다른 사람 0.57–0.64.
- 읽는 법: 학습할 날이 214일뿐이라 딥러닝이 PCA·평균 거리보다 나을 근거가 없다. "새벽 게임"처럼 평소에 없는 칸이 켜지는 이상은 모두 잘 잡고, 시간만 밀리거나 남의 날인 경우는 모두 약하다(0.6 근처).
- 모델 설정(크기, 학습률, 잠재 차원)은 테스트 결과를 보고 바꾸지 않았다. 바꿀 만한 것: 잠재 차원·드롭아웃을 검증 데이터로 고르기, 요일 정보.

## 이 숫자를 얼마나 믿을까 (테스트 세트를 여러 번 봤다)

코드 리뷰 3라운드에서 데이터 정리(중복 행, 세션 경계, 머문 시간)와 평가 방법(새벽 게임 값, 블록 부트스트랩, early stopping 날)을 고칠 때마다 **같은 테스트 세트로 다시 쟀다**. 고친 이유는 모두 버그였고 결과를 좋게 하려던 것은 아니지만, 테스트를 여러 번 보면 그 자체로 결과가 낙관적으로 기운다. 그래서 위 숫자는 "대략 이 정도"로 읽고, 1–2 %p 차이(다음 앱 top-1)는 결론으로 쓰지 않는다. 깨끗한 확인은 처음 보는 데이터(DevDesk 자체 `activity_samples`)로 한 번만 재는 것이다.

## DevDesk 자체 데이터로 첫 실행 (2026-11-02)

`ml/scripts/export_devdesk.py`로 받은 내 `activity_samples`: PC 1대, 10-30 ~ 10-31 이틀, **493분** (브라우저 267, 터미널 83, 게임 72, 기타 53, 채팅 18). 같은 코드에 `--devdesk`로 넣었다.

- 다음 앱 예측: 방문 58번, 세션 7개 → 예제 학습 35 / 검증 8 / 테스트 7. 테스트 세션이 1개라 신뢰구간을 내지 않는다(`MIN_CI_GROUPS` = 10). GRU top-1이 seed마다 0.29–0.71로 흔들려 **아직 아무 결론도 낼 수 없다**.

## 발표에 쓸 결론

- 다음 앱 GRU는 top-1에서 "직전 앱으로 돌아가기"와 비슷하다(+1–2 %p, seed와 데이터 정리에 따라 유의/비유의가 바뀜) — **강한 단순 기준선과 seed 범위를 꼭 같이 보여야** 한다. GRU의 이득은 top-3(후보 3개 추천)에서 나온다.
- 데이터 정리가 결론을 흔들었다(중복 행 → 가짜 A→B→A; 새벽 게임 값 1.0 → 크기만으로 잡힘) — 모델보다 데이터 쪽 확인이 중요했다.
- 데이터가 작으면(하루 214개) 오토인코더보다 PCA가 낫다.
- 이탈 예측은 처음 정의(94 % 이탈)로는 멈췄다. 정의를 "다음 10분 중 업무 시간"으로 바꾸고 문서 앱을 넣자, 예측할 문제가 됐다. DevDesk가 기록하는 정보만으로도 모델이 사람별 평균보다 11–15 % 덜 틀렸다(세 H 모두 유의). GRU와 LightGBM은 비슷했다. 브라우저 절반을 모르는 것이 남은 한계다.
