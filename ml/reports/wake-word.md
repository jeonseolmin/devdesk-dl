## 지표

- **시간당 오작동(FA/h)**: "자비스"가 없는 긴 오디오(스트림)에서 몇 번 울리나. 1.5 s 창을 CNN 100 ms / oww 80 ms마다 밀며 채점, 한 번 울리면 1초 쉼.
- 기준값은 **검증 스트림(2.8 시간)에서** "시간당 0.5회 이하"가 되는 가장 낮은 값으로 정하고, **테스트 스트림(3.0 시간)은** 그 기준값을 재기만 함.
- **놓친 비율**: 그 기준값에서 테스트 정답 76개 중 못 알아들은 비율.

## 읽는 법 / 한계

1. **테스트가 너무 쉽다.** 두 모델 모두 테스트 AP 1.0, 놓친 비율 0–3 %. 정답이 전부 TTS라 실제 목소리와 다르고, 76개뿐이라 1개 = 1.3 %p. 순위를 정하려면 **실제 녹음**(`wake/real/<이름>`)이 필요하다. → 아래 "실제 목소리" 절: TTS 기준 숫자는 실제 성능을 전혀 말해 주지 않았다.
2. **오작동은 모든 데이터 크기에서 CNN이 평균적으로 적다.** 402개 CNN만은 시드에 따라 13.8회까지 올라 전이학습 범위와 겹쳤다. 기본값 0.5에서 CNN은 평균 1–7회/시간, 전이학습은 11–17회/시간이었다. 검증에서 정한 기준값으로 테스트를 재면 CNN은 0–0.3회, 전이학습은 최대 1.3회로 목표(0.5)를 넘기기도 했다. 전이학습 백본은 영어 음성으로 학습돼 영어 단어(Speech Commands)에 더 잘 속는 것으로 보인다(추정, 검증 안 함).
3. **전이학습은 정답 402개 미만이면 평균 4–6 %를 놓쳤고, 시드마다 0–12 %로 크게 흔들렸다.** CNN은 0–1 %였다. 10-31 보고서의 "50개일 때만 특히 나쁘다(10.5 %)"는 시드 하나의 튄 값이었다. 즉 "사전학습이 적은 데이터에 유리하다"는 예상과 달리, 이 데이터에서는 전이학습이 어느 크기에서도 유리하지 않았다. 백본이 한국어 "자비스"와 비슷한 영어 소리를 이미 하나로 묶어 버리는 탓일 수 있다(추정).
4. 기본값 0.5는 쓰면 안 된다: 시간당 최대 21번 울린다. 기준값은 반드시 긴 오답 스트림에서 정해야 한다.
5. 오답 스트림은 영어 단어 + TTS 한국어 문장 6시간 남짓. 실제 책상 소리(키보드, 유튜브, 대화)는 아직 없다.

## 비슷한 단어 (2026-11-02)

"자비스"와 소리가 비슷한 7개 단어(서비스, 자비, 자막, 차비, 자바, 잡지, 저기)를 같은 방법(XTTS 문장 → Whisper 확인 → 자르기)으로 만들었다(`synth_wake.py --word`, 화자당 2문장). 화자 분할은 "자비스"와 같다.
- **평가:** 학습에 쓰지 않은 화자(검증 + 테스트)의 클립으로 한다. 기준값을 정하는 검증 스트림에는 비슷한 단어가 들어 있지 않다.
- **학습(`--confuse-train`):** 학습 화자의 클립 115개를 오답으로 더한다.
- **평가 클립 수:** 서비스 24, 잡지 14, 차비 13, 저기 11, 자비 6, 자막 6, 자바 1. "자바"는 Whisper가 영어 "Java"로 받아 적어 거의 다 걸러졌다.

기준값은 검증에서 시간당 오작동 0.5회이고, 숫자는 시드 3개의 평균(괄호 안은 범위)이다. 모두 학습 정답 402개다.

| 설정 | "서비스"에 깨어남 | 놓친 비율 | 기본값 0.5일 때 FA/h |
|---|---|---|---|
| CNN | 88 % (71–100) | 2.6 % (0–7.9) | 6.5 (1.3–13.8) |
| CNN + 비슷한 단어 학습 | 39 % (25–46) | 1.3 % (0–2.6) | 1.6 (0.3–3.3) |
| 전이학습 | 85 % (79–96) | 0.4 % (0–1.3) | 13.7 (13.5–14.1) |
| 전이학습 + 비슷한 단어 학습 | 5 % (0–12) | 4.8 % (1.3–6.6) | 17.0 (12.8–22.0) |

- **문제는 "서비스" 하나였다.** "~비스"로 끝나는 세 글자라 두 모델 모두 거의 "자비스"로 들었다. 나머지 단어는 학습 전에도 대부분 0 %(가끔 9–17 %)였다.
- **비슷한 단어를 오답으로 넣으면 효과가 컸다.** 전이학습은 85 %에서 5 %로, CNN은 88 %에서 39 %로 줄었다. 대신 전이학습은 진짜 "자비스"를 놓치는 비율이 0.4 %에서 4.8 %로 늘었다. 기준값을 올려야 했기 때문이다(로짓 6.0 → 7.5).
- **실제 쓰기에 무엇이 나은지는 아직 모른다.** CNN + 비슷한 단어 학습은 기본 오작동도 줄었다(6.5 → 1.6회/시간). 놓침과 오인식 중 무엇을 더 줄일지는 실제 목소리로 재 봐야 정할 수 있다.
- **같은 시드로 다시 돌려도 숫자가 달랐다.** CNN 시드 42의 놓친 비율이 1.3 % → 11.8 % → 7.9 %로 바뀌었다(GPU 연산 순서 차이로 추정). 그래서 이 절부터는 시드 3개의 범위로 적는다. 아래 학습 개수별 표도 시드 3개로 다시 쟀다.

## 실제 목소리 (2026-11-02 밤)

본인이 헤드셋(Razer Barracuda X)으로 "자비스" 40개, "자비스가 아닌 말" 30개(비슷한 단어 + 평소 말)를 녹음했다(`record_wake.py`, 1.5 s, 16 kHz). 녹음은 `ml/data/wake/real*`에만 있다.

- **평가:** 녹음 순서로 앞 20개는 학습용, 뒤 20개("자비스")와 10개("다른 말")는 시험용으로 나눴다(`--real-train 20`). 녹음 학습 없는 기준 모델(`--real-copies 0`, `_hold20`)도 **같은 시험 녹음**으로 쟀다. 기준값은 지금까지처럼 검증 스트림의 오경보 ≤0.5회/시간이다. 모두 비슷한 단어 학습(`--confuse-train`)을 켰다.
- **학습:** 앞 20개 + 20개를 20번씩 반복해(매번 새 증강) 학습에 더했다. 반복분이 있어도 한 epoch의 학습 단계 수는 기준 모델과 같다(CNN 51 = 51, `epoch_share`). 처음 잰 표는 반복분만큼 단계가 몇 % 많아 다시 쟀다.

차트: `figures/wake_real.png`.

| 설정 | 내 "자비스" 놓친 비율 (20개) | "다른 말"에 깨어남 (10개) | TTS 놓침 | 테스트 FA/h |
|---|---|---|---|---|
| CNN, TTS만 (시드 3개) | **100 %** (100–100) | 0 % | 0–7 % | 0 |
| CNN + 내 녹음 20개 (시드 3개) | **22 %** (10–40) | 0 % | 1–3 % | 0.33–0.66 |
| 전이학습, TTS만 (시드 1개) | 95 % | 0 % | 7 % | 0.33 |
| 전이학습 + 내 녹음 20개 (시드 1개) | 75 % | 0 % | 21 % | 0 |

- **TTS만으로는 실제 목소리에 전혀 일반화되지 않았다.** TTS 시험에선 0–7 %만 놓친 CNN이 내 목소리는 시드 3개 모두 하나도 못 들었다(녹음당 가운데 창 하나 기준). 위 표들(TTS 기준)의 "놓친 비율"은 실제 사용 성능을 말해 주지 않는다.
- **내 녹음 20개만 넣어도 CNN은 평균 22 %로 내려갔다.** 시드마다 10–40 %로 흔들렸다(20개 중 2–8개). 전이학습은 같은 녹음으로 95 → 75 %에 그쳤고 TTS 놓침이 21 %로 늘었다(기준값 로짓 7.5 → 8.7). 미리 학습된 임베딩이 20개로는 한 사람 목소리에 맞춰지지 않은 것으로 보인다(추정, 시드 1개).
- **앱 모델:** 측정 후 녹음 70개 전부로 다시 학습한 `wake_cnn_confuse_real40`(기준 로짓 1.69, TTS 놓침 2.6 %)을 `wake.onnx`로 내보냈다. 테스트 스트림에선 시간당 0.98회로 목표 0.5를 넘었다(검증에서 정한 기준값을 테스트가 재기만 한 결과). 전부 학습에 썼으므로 실제 녹음 성능은 따로 잴 수 없다(가까운 참고값은 위 22 %지만, 모델도 재는 방식도 앱과 달라 앱의 놓침률로 읽으면 안 된다).
- **한계:**
  - 화자가 한 명(본인)이다. 시험 녹음도 같은 사람, 같은 헤드셋, 같은 날이라 "처음 보는 목소리"가 아니라 "내 목소리의 다른 녹음"을 잰 것이다(규칙 "화자 단위로 나눈다"의 예외, `AGENTS.md`).
  - 시험 "자비스" 20개 = 1개당 5 %p, "다른 말" 10개는 오경보율을 말하기엔 너무 적다.
  - 놓친 비율은 녹음 1개당 가운데 창 하나만 쟀다. 앱은 0.1초마다 창을 밀며 그중 하나만 넘으면 깨어나므로, 이 표는 앱의 실제 반응과 다르다. 학습한 모델을 앱 방식으로 잰 값은 없다(`docs/troubleshooting.md`의 2/40은 TTS만 학습한 옛 모델을 녹음 40개로 잰 값이다).
  - 1.5초 녹음은 창 길이와 같아 복사본마다 단어 위치가 그대로다(게인과 잡음만 바뀐다). 실제 녹음은 한 정렬만 학습한다.
  - 복사본을 정답과 "다른 말"에 같은 수로 넣어도, 음성 풀이 훨씬 커서 배치 안에서는 헤드셋 소리의 정답 비중이 약 7배 크다. 모델이 "이 마이크 소리 = 자비스"를 일부 배웠을 수 있고, 시험 "다른 말"이 적어 이 표로는 가려내지 못한다.
  - 전이학습은 실제 정답을 `--pos-copies`로 한 번 더 늘려 임베딩한다(시간만 더 듦).
  - 녹음 번호(파일 이름 순서)로 앞뒤를 나누므로, 파일을 지우거나 다시 녹음하면 시험 세트가 바뀐다. 위 표는 녹음 70개가 고정된 뒤 한 세트로 쟀다. 같은 시드라도 GPU 때문에 재실행마다 숫자가 조금 달라진다(CNN 기준 모델 시드 42의 TTS 놓침 5.3 → 6.6 %).
  - 처음 돌린 1회(시드 42)에는 테스트 중 실수로 녹음된 방 소리 3개가 "다른 말"로 섞여 있어 95 %로 낙관적이었다. 그 파일은 지우고 위 표를 다시 쟀다.

## 겪은 문제 (발표 "어려웠던 점")

- XTTS에 "자비스" 한 단어만 주면 뒤에 몇 초짜리 엉뚱한 소리를 붙였다(Whisper가 "뇌 뇌 뇌 사비스"로 받아 적음). → 문장 첫 단어로 말하게 하고 잘라냄.
- openWakeWord 멜 모델은 입력 전체의 최댓값 기준으로 조용한 칸을 깎아서, 긴 오디오를 한 번에 넣으면 같은 구간의 값이 5–20 % 달라졌다. → 스트림도 1.5 s 창마다 따로 임베딩(데모와 같은 방식).
- 처음엔 기준값을 테스트 스트림에서 정하고 같은 테스트로 성적을 냈다(낙관적). → 검증 스트림으로 분리.
- 시그모이드 점수 0.05–0.999 칸에서 기준값을 고르니 전이학습 모델 점수(0.999 근처)가 구분되지 않아 "50개 모델 63 % 놓침"이라는 틀린 숫자가 나왔다. → 로짓에서 실제 점수 값으로 정확히 찾음.
